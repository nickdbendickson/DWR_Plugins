changelog=0.17.46 (2026-10-26; tool 7b: inventory max-pool area fallback, Runner report water-body mask)
    * Tool 7b surface area: when a curve folder is given but the dam's tool-3 stage-storage curve is too shallow (spans less than half the dam height), missing, or gives no area, the Runner's AREA_AC is now the DWR inventory's maximum-pool area (max_pool_area, acres; the DWR records max pool at the top of dam, the level AREA_AC means) instead of nothing, with a warning naming the dam. No inventory area (0 or blank) = no area, as before, with a warning saying so. Where the area came from (surface_area_source = stage_storage / inventory_max_pool_area / none) is in the new output field rn_area_src, the dam.json source note of surface_area_ac, the log and the run manifest (extra.surface_area_source per dam). Dams with a usable curve, and runs with no curve folder, are unchanged.
    * Tool 1 writes the new field inv_maxa_m2 (m2, from DWR max_pool_area / max_pool_a; empty for NID dams, which have no max-pool area). A dams layer from an older tool 1 lacks it: tool 7b warns and the fallback reads a max_pool_area / max_pool_a field kept on the layer, if any. Rerun tool 1 to use it.
    * Tool 7b water-body mask (advanced; the window: Settings, 'Step 7b: mask existing lakes and ponds in the Runner's report', off by default, uses the Inputs NHD waterbodies layer): sent to the Runner's WATER_MASK (Runner 3.10.27 or later), which gives the report's flooded area and speeds with and without the existing lakes and ponds; the flood model, rasters and class do not change. Default sends nothing. Recorded in rn_inputs and the run manifest (extra.water_mask). Test: tests/test_7b_area_fallback_watermask.py.

    0.17.44 (2026-10-24; tool 1 writes the DWR/NID field map it never saved)
    * Tool 1 (Prepare dams) now writes the chosen DWR/NID field names to <work>/1_fields.json next to the standardized-dams output. The writer existed but was never called, so the reader (core/workflow.py step 1) looked for a file nothing produced and re-detected the fields on every chain run.     0.17.43 (2026-10-24; dam.json surface_area_ac and dam_length_ft)
    * Tool 7b's dam.json (core/damrecord_io.py) now has dam_length_ft: the length of the mapped dam line (tool 4's crest_len_m on the breach point), else the inventory's dam length (tool 1's crest_len_m: DWR dam_length / NID DAM_LENGTH) - the order tool 5 uses - with where it came from in the source note. Before, it was never written, so the Runner used its 400 ft default crest length. A run of an existing folder now takes this length for the crest-raise strip, the PMF overtopping weir and the HEC-RAS dam connection, so results can change on a rerun.
    * surface_area_ac (the area at the top of dam the Runner reads for AREA_AC) is still only the area tool 7b sends from the tool-3 curve. When there is none it is written as null with the reason in its source note (the shallow-curve note, or no curve), quoting the inventory's normal-pool area when there is one; that area is not written, since the Runner would read it as the top-of-dam area. dam_length_ft with no line and no inventory length is a null with a note too. A null never replaces a value another tool recorded, and a later value fills it with no conflict.
    * Existing dam.json files get the fields on the next tool 7b run. Tests: tests/test_handoff_record_fields.py, tests/test_suite09.py.
    0.17.42 (2026-10-22; Download DEM downstream bearing)

    0.17.40 (2026-10-20; Von Thun & Gillette parity; renumbered from 0.17.33)
    * Von Thun & Gillette (1990) breach width: Cb now steps at 1,000 / 5,000 / 10,000 ac-ft (a volume on a limit is in the larger class), the method's limits and the Runner's (core/breach.py vtg_1990). The rounded m3 limits used before (1.23e6 / 6.17e6 / 1.23e7 m3) put reservoirs of 997.2-1,000, 5,000-5,002 and 9,972-10,000 ac-ft in the next class, so their VTG-E / VTG-R breach was 12.2-24.4 m wider than the Runner's. Other volumes and the other methods are unchanged. New tests/test_vtg_parity.py compares the two plugins on both sides of each limit.
    0.17.39 (2026-10-20; gdal.Warp without source overviews; renumbered from 0.17.35)

TerrainLoader.load (the larger-clip terrain), Find Ponds' terrain warp and its local-DEM clip, the terrain cache's local-DEM clip and Download DEM's local DEM (write_local_dem) now read the full-resolution cells.     0.17.29 (2026-10-19)
    * Download DEM has a third source, 'USGS 3DEP 1 m lidar tiles (native, TNM)' (core/lidar_tnm.py): the 3DEP 1 m lidar project tiles themselves (10 km GeoTIFFs at 1 m, NAD83 UTM metres, about 275 MB each) from The National Map Access API, not the resampled ImageServer image. Area: a box (BBOX), else a dam folder (DAM_FOLDER: the Runner's model bounds plus DOMAIN_PAD_M, else dam.json's point and the buffer), else the dam point and buffer, else the county; never the state. The first run lists the tiles (project, collection and publication dates, size), the total, what is still to download and the free disk space, and downloads nothing; LIDAR_DOWNLOAD downloads them (refused over LIDAR_MAX_GB, default 10, or when less than 2 GB would stay free). Tiles go to TILE_FOLDER, else <suite data folder>/dem/lidar_1m/, else <output>/lidar_1m (never the offline pack or a read-only folder); tiles already there are skipped, a cut download resumes from its .part (HTTP Range), each tile is retried 4 times and checked (size, GDAL opens it at 1 m with a CRS), and lidar_1m_manifest.json records tile, project, dates, URL, sha256 and bytes. Where two projects publish the same tile the newest collection is used and the log says so (LIDAR_KEEP_OLDER keeps the older one underneath). The result is <DAM_ID>_1m_lidar.vrt in the output folder (1 m, the tiles' UTM zone, newest collection on top, the coarser DEM underneath: FALLBACK_DEM, else <DAM_ID>_10m_5070.tif when it is there), <DAM_ID>_1m_lidar.json (projects, tiles, dates, fallback) and the _dem.txt facts. Cancel keeps finished tiles. Nothing downloads on open. damsuite 1.17.4: suitedata skips dem/lidar_1m, so the tile cache is never taken for your own DEM.

    0.17.27 (2026-10-19)
    * Tool 3 honours the window's storage choice: new parameter 'Storage to use' (STORAGE_CHOICE: Max storage, the default / Normal storage / Larger of the two; the window's labels and values). Max raises the storage at the top of dam to the inventory maximum (as before); Normal keeps the DEM-measured part above the normal pool; Larger uses whichever inventory value is larger. A missing or zero value falls back to the other one (Normal without a normal storage uses the maximum; Max without a maximum uses the normal) and says so as a warning; with neither the DEM estimate is kept. Dams without a water body use the chosen value for the full-height inventory curve. stor_notes and the log start with the storage used and any fallback (no new field: tools 16 and 19 write the storage fields by position). The window no longer sends STORAGE_CHOICE to tool 1, which never had it. A model or script without the parameter gets Max.
